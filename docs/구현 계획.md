## 1단계. DB 테이블

### 할 일

1. `schema.sql`을 저장소 루트에 작성한다. PRD 9.1~9.3절의 테이블 7개 + `tf_ai_logs`.
   - `tf_ai_logs`에는 **나중에 README 7.1절 5항의 근거로 쓸 열**을 빠뜨리지 않고 넣는다:
     `called_at`(시각, `timestamptz`), `attempt_no`(몇 차 모델인지 1~3, 앱 자체 배정은 4),
     `model`(모델 이름), `outcome`(성공/시간초과/빈 응답/오류/검사 실패),
     `fail_reason`(실패 이유를 사람이 읽을 수 있게), `elapsed_ms`(걸린 시간), `response_excerpt`(응답 앞부분)
   - `called_at`은 UTC로 저장하고 **화면에 보여 줄 때만 KST로 변환**한다.
2. 제약을 빠뜨리지 않고 넣는다:
   - `tf_members`: `(team_id, slot_no)` 기본 키, `student_id` 유일, `slot_no` 1~4 범위 검사
   - `tf_votes`: `(application_id, voter_id)` 기본 키
   - `tf_students.student_no` 유일, `main_role`에 역할 6개만 허용
   - `tf_student_sub_roles.role`에 역할 6개만 허용
   - `tf_teams.name` 유일
3. Supabase SQL 편집기에서 `schema.sql`을 실행해 테이블을 만든다.
4. `db.py`를 만든다: `.env`(로컬)와 `st.secrets`(배포)에서 `DATABASE_URL`을 읽고, **연결을 한 번만 만들어 재사용**한다(`st.cache_resource`).
5. 상태 초기화 함수(`reset_all`)와 `tf_settings` 읽기/쓰기 함수를 만든다.

### 끝나면 확인할 것

- [ ] Supabase에 `tf_`로 시작하는 테이블 8개가 보인다
- [ ] `tf_ai_logs`에 `called_at`, `attempt_no`, `outcome`, `fail_reason` 열이 있다
- [ ] `tf_` 아닌 테이블(6장 실습 테이블)은 건드리지 않았다
- [ ] 같은 `(team_id, slot_no)`에 두 번 넣으면 **DB가 오류를 낸다** (직접 SQL로 시험)
- [ ] 이미 팀이 있는 학생을 다른 팀에 넣으면 **DB가 오류를 낸다**
- [ ] `slot_no`에 5를 넣으면 **DB가 오류를 낸다**
- [ ] `main_role`에 "코딩왕"을 넣으면 **DB가 오류를 낸다**

### 4-1. 규칙 검사 함수 (코드로만, 화면 없음)

규칙 판정을 순수 함수로 먼저 만든다. 화면과 섞지 않는다.

1. `주역할_중복(팀, 지원자)` — 팀원의 **주 역할**만 본다
2. `최대매칭(사람들)` — {기획자, 웹 프로그래머} 2자리에 서로 다른 사람을 짝지은 최대 개수 (한 사람이 둘 다 가능해도 1자리)
3. `필수역할_자리_모자람(팀, 지원자)` — PRD 4.2절 공식
4. `지원_가능(학생, 팀)` — 막히는 이유를 **순서대로** 판정해 첫 이유를 돌려준다

- [ ] 보조 역할은 주 역할 중복 판정에 **쓰이지 않는다**

### 4-2. 지원 기능

1. 팀 목록을 `team_1`, `team_2`, … 컨테이너로 그린다. 팀원 이름 + 주 역할 + 보조 역할을 보여 준다.
2. 내 팀에 "내 팀" 표시, 팀이 없으면 "아직 팀이 없음".
3. 팀마다 `apply_1`, `apply_2`, … 단추.
4. **이미 팀 있음 / 결과 기다리는 지원 있음 / 마감** → 단추를 **숨기거나 비활성화**.
5. 그 밖에 막히는 경우는 단추를 눌렀을 때 `result`에 `막힘: 이유`.
6. 빈 팀에 지원하면 **바로 승인**하고 `tf_members`에 넣는다.
7. 팀원이 있으면 `tf_applications`에 `대기`로 넣고 `result`에 `대기`.

- [ ] 중간 3단계: 학생2(PL;TT)가 팀1(학생1 주역할 PL)에 지원 → `막힘` (주 역할 중복)

- [ ] 이미 팀이 있는 학생에게는 지원 단추가 없거나 비활성이다

### 4-3. 투표 기능

1. 내 팀에 들어온 대기 지원마다 `vote_yes_{지원자 학번}`, `vote_no_{지원자 학번}` 단추.
2. 투표하면 `tf_votes`에 넣는다. **이미 투표했으면 단추를 숨기거나 비활성화**하고 "내 투표: 찬성"처럼 보여 준다.
3. 한 명이라도 **거부** → 기다리지 않고 바로 `거절`.
4. 아직 투표하지 않은 팀원이 있으면 `대기`.
5. 투표할 사람은 **투표하는 때의 팀원**이다. 팀원이 늘면 그 사람도 투표해야 승인된다.
6. `result`에 그 지원의 지금 상태(`승인`/`대기`/`거절`)를 보여 준다.

#### 끝나면 확인할 것

- [ ] 쉬움 4단계: 학생7이 팀1에 지원, 학생1 찬성 + 학생4 거부 → `거절`

- [ ] 이미 투표한 지원에는 그 학생의 찬성·거부 단추가 없거나 비활성이다

### 4-4. 승인 직전 재검사 (어려운 해결 3점)

1. 모든 팀원이 찬성한 **그 순간** 규칙을 다시 검사한다: 정원 / 주 역할 중복 / 필수 포함 역할 자리.
2. 어기면 `거절`로 바꾸고 `tf_applications.reason`에 이유를 남긴다.
3. 처리 순서는 **투표가 끝난 순서**(`resolved_at`)로 한다. 지원한 순서가 아니다.
4. 그 전에는 대기 중인 지원을 **미리 거절하지 않는다**.
5. 팀원 자리 넣기는 **DB 유일성 제약에 맡긴다**. 오류가 나면 `거절`로 처리한다 (어려운 해결 0.5점).

#### 끝나면 확인할 것

- [ ] **어려움 6~8단계**가 그대로 재현된다:
  - 6단계: 학생5·학생6이 차례로 팀2에 지원 → 둘 다 `대기`
  - 7단계: 학생2·학생8이 학생5에 찬성 → `승인`
  - 8단계: 학생2·학생8·학생5가 학생6에 찬성 → **`거절` (승인 직전 검사)**

## 6단계. AI 배정

### 할 일

1. OpenRouter에서 **무료 텍스트 생성 모델 3개**를 골라 1차·2차·3차로 정한다 (이름이 `:free`로 끝나는 것). **`openrouter/free` 라우터는 쓰지 않는다**.
2. 모델 이름을 코드 상수나 설정으로 둔다. 키는 `.env` / `st.secrets`에서만 읽는다.
3. 프롬프트를 만든다: 지금의 팀 구성 + 팀이 없는 학생과 주/보조 역할 + PRD 4장 규칙 + **JSON 형식으로만 답하라**는 지시.
4. `reasoning effort`를 `low`로, `max_tokens`를 넉넉히 준다.
5. `admin_assign` 단추를 만든다.
6. 응답을 파싱해 배정안을 만들고 **검사 5가지**(PRD 6.1절)를 모두 돌린다.
7. 통과한 배정안만 관리자에게 보여 준다: 학생 이름, 역할, 배정된 팀.
8. `admin_confirm` 단추로 확정하면 `tf_members`에 저장한다.
9. 배정 전에 **"규칙을 지키는 배정이 아예 없는지" 먼저 확인**한다. 없으면 AI를 부르지 않고 `assign_status`에 "규칙을 지키는 배정이 없음" + 이유.
10. **AI 호출이 실패할 때마다** `tf_ai_logs`에 한 행을 남긴다. 성공한 호출도 함께 남긴다.
    - 반드시 들어갈 것: **시각(`called_at`)**, **몇 차 모델(`attempt_no`)**, **실패 이유(`outcome` + `fail_reason`)**
    - 함께 남길 것: 모델 이름, 걸린 시간, 응답 앞부분
    - 3차까지 실패해 앱이 스스로 배정한 경우도 `attempt_no = 4`로 한 행 남긴다
    - 이 기록이 **README 7.1절 5항(AI 호출 실패 사례)의 근거**가 된다. 나중에 되돌아볼 수 없으므로 처음부터 남긴다
    - 기록에 **API 키를 넣지 않는다** (감점 8번)
11. **관리자 화면 "현황" 부분에 AI 호출 기록 표를 보여 준다.** `tf_ai_logs`를 최근 순으로 읽어 그린다.

    | 시각 (한국 시각) | 차수 | 모델 이름 | 결과 | 실패 이유 |
    | --- | --- | --- | --- | --- |
    | 2026-10-30 14:22:05 | 1차 | (모델 이름) | 실패 | 120초 안에 응답 없음 |
    | 2026-10-30 14:24:08 | 2차 | (모델 이름) | 성공 | — |

    - **시각은 KST로 변환해** 보여 준다. DB에는 UTC(`timestamptz`)로 저장되어 있다.
    - 차수는 `attempt_no`를 `1차`/`2차`/`3차`/`앱 자체 배정`으로 바꿔 쓴다.
    - 결과는 `outcome`(성공/시간초과/빈 응답/오류/검사 실패), 실패 이유는 `fail_reason`.
    - 이 표가 README 7.1절 5항 사례를 찾을 때 **어느 시각의 어느 호출이었는지** 알려 준다. 화면 캡처 한 장으로 근거가 된다.
    - 표에 **API 키를 넣지 않는다**. `response_excerpt`를 보여 줄 때도 키가 섞이지 않게 한다 (감점 8번).

## 7단계. AI 실패 처리 — **어려움 12점의 핵심**

### 할 일

1. **모델마다 120초 전체 대기 시간**을 잰다. 요청 함수의 timeout 값만 주는 것으로는 부족하다 — 응답이 천천히 오는 경우까지 재서 끊는다 (어려운 해결 1점).
2. 실패로 보는 경우를 모두 처리한다: 응답 없음, **빈 응답**, 오류(HTTP 429 등), 검사 5가지 실패.
3. 실패하면 1차 → 2차 → 3차 모델로 자동으로 넘어간다.
4. `assign_status`에 **몇 차 모델을 기다리는 중인지** 보여 준다 (어려운 해결 1점). 예: `2차 모델 응답 대기 중 (45초 경과)`.
   - **실패해서 다음 모델로 넘어갈 때는 그 사실을 글자로 남긴다.** 예:

     ```
     1차 모델 실패(120초 안에 응답 없음) → 2차 모델로 넘어감
     2차 모델 응답 대기 중 (45초 경과)
     ```

   - 줄을 **지우지 않고 쌓아서** 보여 준다. 배정이 끝난 뒤에도 무슨 일이 있었는지 화면에 남아 있어야 README 7.1절 5항의 근거로 캡처할 수 있다.
   - 실패 이유는 `tf_ai_logs.fail_reason`에 넣는 것과 **같은 문장**을 쓴다.
   - 3차까지 실패하면 `3차 모델 실패(...) → 앱이 스스로 배정함`을 남긴다.
5. **3차까지 실패하면 앱이 스스로 배정한다** — 검사 5가지를 모두 통과하는 배정을 **모든 경우를 따져 끝까지 찾는다** (어려운 해결, 최대 6.5점).
   - 배정 대상은 **8명 이하**이므로 가지치기를 넣은 완전 탐색으로 충분하다.
   - 가지치기: 주 역할 중복이 생기는 배치를 즉시 버린다, 남은 자리로 필수 역할을 채울 수 없는 상태를 즉시 버린다.
   - 찾으면 그 배정을 보여 준다. 끝까지 없으면 "규칙을 지키는 배정이 없음" + 이유.
6. **전체 시간 제한**을 둔다. 배정 전체가 10분을 넘지 않게 한다 (감점 18번).

### 시험 방법의 원칙 (중요)

실패 처리를 시험하는 방법과, README에 적을 사례는 **엄격히 구분한다**.

| 구분 | 쓰는 곳 | 쓰지 않는 곳 |
| --- | --- | --- |
| **모델 이름을 일부러 틀리게 해서 실패시키기** | **코드가 제대로 동작하는지 내가 확인하는 용도로만** 쓴다. 무료 모델 하루 한도를 쓰지 않고 2차·3차 전환과 자체 배정을 확인할 수 있다 | **README 7.1절 5항에 쓰지 않는다.** 내가 만든 가짜 실패이므로 사례가 아니다 |
| **연습하다 진짜로 생긴 실패** | **README 7.1절 5항의 AI 실패 사례는 이것만 쓴다.** 예: 1차 모델이 120초 안에 응답하지 않음, HTTP 429로 거절됨, 빈 응답, 배정안이 검사에서 걸러짐 | — |

- 진짜 실패는 **언제 생길지 모르므로**, 연습 시나리오를 돌릴 때마다 `assign_status` 화면을 보고 실패가 보이면 **그 자리에서 화면을 `img/`에 저장**한다.
- `tf_ai_logs`의 해당 행(시각·차수·실패 이유)을 README 사례의 근거로 함께 적는다.
- 꾸며 낸 사례는 **6.3절 20번으로 시나리오 밖 점수가 0점**이 된다. 지어내지 않는다.

### 끝나면 확인할 것

- [ ] 1차 모델 이름을 일부러 틀리게 해 실패시키면 **2차 모델로 넘어간다**
- [ ] 세 모델 이름을 모두 틀리게 하면 **앱이 스스로 배정한다**
- [ ] 앱이 스스로 만든 배정이 검사 5가지를 모두 통과한다
- [ ] 어려움 시나리오(배정 대상 8명)에서 완전 탐색이 **몇 초 안에** 끝난다

## 9단계. 연습 시나리오 자동 테스트 프로그램

부록의 연습 시나리오 3개를 **자동으로 끝까지 돌려서**, 단계마다 기대 결과와 실제 결과를 맞춰 보는 프로그램을 만든다. 손으로 32단계(6+11+15)를 매번 해 보는 것은 고치고 다시 확인할 때마다 너무 오래 걸린다.

### ⚠️ 가장 먼저 지킬 것 (감점 19번, 그 시나리오 0점)

- 테스트 프로그램과 시나리오 데이터는 **`tests/` 폴더에만** 둔다.
- **`streamlit_app.py`와 앱 코드는 `tests/`의 어떤 파일도 읽지 않는다.** `import`도 하지 않는다.
- 앱이 학생 이름이나 단계 순서를 보고 결과를 다르게 내면 **그 시나리오 점수가 0점**이다. 앱은 규칙만 보고 판단해야 한다.
- 테스트가 앱에 넣는 것은 **CSV와 화면 조작뿐**이다. 기대 결과를 앱에 알려 주지 않는다.

### 할 일

1. 시나리오를 **데이터 파일**로 적는다. `tests/scenarios/쉬움.json`, `중간.json`, `어려움.json`.
   - 각 단계: 단계 번호, 하는 일(누가·무엇을), 기대하는 `result` 첫 단어(`승인`/`대기`/`거절`/`막힘`)
   - 부록 표를 그대로 옮긴다. 쉬움 6단계, 중간 11단계, 어려움 15단계
2. 브라우저를 자동으로 조작하는 방식으로 만든다 (**채점 프로그램과 같은 방식**). Playwright를 쓴다.
   - 화면 요소는 **2.7절 `key`로만** 찾는다. 이러면 `key`가 틀렸는지도 함께 확인된다 (감점 15번 예방).
   - **확인됨 (2026-10-23, Streamlit 1.66.1):** `key`를 준 요소는 화면에서 `st-key-<key>` 라는 class 를 가진다.
     - 입력칸: `.st-key-login_student_no input`
     - 단추: `.st-key-login_submit button`
     - 표시 영역: `.st-key-result`, `.st-key-whoami`
     - 앱을 띄워 `st-key-whoami`, `st-key-result`, `st-key-login_student_no`, `st-key-login_password`, `st-key-login_submit` 다섯 개가 실제로 나오는 것을 눈으로 확인했다.
   - Streamlit 판이 올라가면 이 규칙이 바뀔 수 있으므로, `requirements.txt`의 판을 고정해 두고 배포 뒤 한 번 더 확인한다.
3. **학생마다 브라우저 창(컨텍스트)을 따로** 쓴다. 채점 프로그램이 그렇게 하므로 같게 맞춘다. 한 창에서 여러 학생으로 번갈아 로그인하면 실제 채점과 다른 상태가 된다.
4. 시나리오 시작 전에 관리자로 로그인해 그 시나리오의 CSV와 팀 수를 올린다(초기화).
5. 단계마다 동작을 실행한 뒤 `result`의 **첫 단어**를 읽어 기대와 비교한다.
6. 결과를 **표**로 출력한다.

   ```
   === 부록 3. 어려움 (어려움.csv, 팀 4개) ===
   단계  하는 일                                    기대    실제    판정
    1   학생1이 팀1에 지원                          승인    승인    맞음
   ...
    8   학생2·학생8·학생5가 학생6에 찬성             거절    승인    틀림
   ...
   ───────────────────────────────────────────────
   15단계 중 14개 맞음, 1개 틀림
   틀린 단계: 8
   ```

7. 지원이 막힌 단계의 **뒤따르는 투표는 건너뛴다**(부록 규칙). 건너뛴 단계는 `건너뜀`으로 적는다.
8. 마지막에 **브라우저를 새로 열어** 확정된 팀 구성을 읽고 규칙을 검사한다 (채점 6.2절 5항과 같게):
   - 모든 팀이 2~4명 / 주 역할 중복 없음 / 기획자·웹 프로그래머가 서로 다른 사람으로 1명씩 / `unassigned`가 비어 있음
9. 세 시나리오를 한 번에 돌리는 명령을 만든다. 예: `python tests/run_scenarios.py --all`
10. AI 호출 수를 아끼기 위해, 배정 단계는 **옵션으로 끌 수 있게** 한다(`--skip-ai`). 지원·투표 규칙만 빠르게 확인할 때 쓴다.
