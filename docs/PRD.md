## 1. 목표와 범위

### 1.1 한 줄 정의

가상 학생들이 스스로 팀에 지원하고 투표해 팀을 만들고, 마감 뒤 남은 학생은 AI가 배정안을 내고 **앱이 그 배정안을 규칙으로 검사**하는 웹 앱.

### 1.2 성공 기준

1. 채점 프로그램이 2.7절의 `key`로 모든 화면 요소를 찾아 자동 조작할 수 있다.
2. 결과 안내(`result`)의 첫 단어가 항상 `승인` / `대기` / `거절` / `막힘` 중 하나다.
3. 확정된 팀 구성이 2.3절의 모든 규칙(정원 2~4명, 주 역할 중복 없음, 필수 포함 역할 충족)을 지킨다.
4. AI가 3차 모델까지 실패해도 앱이 스스로 규칙을 지키는 배정을 만든다.
5. 3장 표의 8개 기능을 **모두 어려운 해결**로 구현한다.

### 1.3 범위에서 빼는 것

- 구글 로그인(`st.login`) — 채점자가 학생 여러 명으로 로그인할 수 없어 쓰지 않는다.
- 학생이 역할을 직접 바꾸는 기능 — 역할은 명단 CSV로만 정해진다.
- 기존 팀원을 다른 팀으로 옮기는 배정 — AI 배정은 팀이 없는 학생만 넣는다.
- 실제 사람의 이름·학번 — 가상 명단만 쓴다(6.3절 9번, -3점).

## 2. 등장인물과 권한

| 사용자 | 로그인 | 할 수 있는 일 |
| --- | --- | --- |
| 학생 | 학번 + 비밀번호(`1234`) | 팀 목록·팀원·팀원의 주 역할과 보조 역할 보기, 팀에 지원, 내 팀에 들어온 지원에 찬성/거부 |
| 관리자(교수) | 학번 `admin` + `ADMIN_PASSWORD` | 명단 올리기(초기화), 모집 마감, AI 배정 요청, 배정안 확인·확정 |

- 관리자 계정은 앱이 시작할 때 비밀 값 `ADMIN_PASSWORD`로 **만들거나 비밀번호를 갱신**한다.
- 명단을 다시 올려도 관리자 계정은 **남긴다**.
- 학생 계정으로 관리자 기능을 쓸 수 없어야 한다(6.3절 11번, -3점).

## 3. 명단과 역할

### 3.1 역할 6개

기획자 · 웹 프로그래머 · 프론트엔드 디자이너 · 테스터 · 보고서 작성자 · 발표자

- 학생마다 **주 역할 1개**와 **보조 역할 0~2개**가 명단 CSV에 정해져 있다. 학생이 바꾸지 않는다.
- 학생 비밀번호는 모두 `1234`.

### 3.2 CSV 형식 (UTF-8 BOM)

```
student_no,name,main_role,sub_roles
2026001,가나다,기획자,보고서 작성자
2026002,라마바,웹 프로그래머,
2026003,사아자,테스터,기획자;발표자
```

| 규칙 | 내용 |
| --- | --- |
| 인코딩 | BOM이 붙은 UTF-8. **반드시 `utf-8-sig`로 읽는다** |
| 열 수 | 항상 4개. `sub_roles`가 없으면 마지막 쉼표 뒤를 비워 둔다 |
| 보조 역할 2개 | `;`로 구분 (`기획자;발표자`) |
| 역할 값 | 3.1절의 6개 중 하나만 허용 (DB check 제약으로도 막는다) |

## 4. 팀 규칙 (2.3절)

| 규칙 | 내용 | 적용 시점 |
| --- | --- | --- |
| 팀 수 | 관리자가 명단을 올릴 때 넣은 수만큼 빈 팀 생성 (팀1, 팀2, …) | 명단 올리기 |
| 정원 | **확정한 팀 구성**에서 모든 팀이 2~4명 (빈 팀 없음) | 지원·배정 |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 됨 | 지원·승인 직전·배정 |
| 필수 포함 역할 | 모든 팀에 **기획자 역할 학생**과 **웹 프로그래머 역할 학생**이 **서로 다른 사람으로** 1명씩 | 지원·승인 직전·배정 |

### 4.1 주 역할과 보조 역할의 쓰임 (중요)

- **주 역할**: 팀 안의 중복을 따지는 **유일한** 기준. 보조 역할은 중복 판정에 쓰지 않는다.
- **보조 역할**: 필수 포함 역할(기획자/웹 프로그래머)을 맡을 수 있는지 따질 때**만** 쓴다.
- 예: 주 역할이 테스터, 보조 역할이 기획자인 학생은 그 팀의 기획자를 맡을 수 있다.

### 4.2 필수 포함 역할 자리 계산 (3장 "어려운 해결" 7점의 핵심)

지원을 막을지 판단하는 공식:

```
남는 자리 = 4 - (현재 팀원 수 + 1)          # 지원자가 들어간 뒤
미충족 필수 역할 수 = 2 - (최대 매칭 수)
    # 매칭: {기획자, 웹 프로그래머} 2자리에
    #       (현재 팀원 + 지원자)를 서로 다른 사람으로 짝지을 수 있는 최대 개수
    #       한 학생이 둘 다 할 수 있어도 1자리만 셈

if 남는 자리 < 미충족 필수 역할 수:  →  "막힘: 필수 포함 역할 자리"
```

검증 예시(부록 3, 11단계):

| 항목 | 값 |
| --- | --- |
| 팀3 현재 팀원 | 학생11(테스터;발표자), 학생15(발표자;프론트엔드 디자이너) — 2명 |
| 지원자 | 학생14(보고서 작성자;테스터) |
| 기획자/웹 프로그래머 가능한 사람 | 없음 → 최대 매칭 0 → 미충족 2 |
| 남는 자리 | 4 - 3 = 1 |
| 판정 | 1 < 2 → **막힘** ✓ (기대 결과와 일치) |

다른 예시: 테스터와 발표자만 있는 2명 팀에 보고서 작성자가 지원 → 남는 자리 1, 미충족 2 → 막힘.

### 4.3 끝까지 필수 역할을 채울 수 없는 팀

지원과 투표를 하다 보면 웹 프로그래머를 맡을 사람 없이 4명이 찬 팀이 생길 수 있다. 이 팀은 더 넣을 수 없고, 마감 뒤 배정에서도 기존 팀원을 옮기지 않으므로 끝까지 채우지 못한다. 이때는 배정 단계에서 `assign_status`에 "규칙을 지키는 배정이 없음"과 이유를 보여 준다(2.5절 8항).

## 5. 지원과 투표 (2.4절)

### 5.1 투표 흐름

| 상황 | 규칙 |
| --- | --- |
| 빈 팀에 지원 | 투표할 팀원이 없으므로 **바로 승인** |
| 팀원이 있는 팀에 지원 | **대기**. 그 팀의 팀원 모두가 투표. 투표할 사람은 **투표하는 때의 팀원** |
| 모든 팀원이 찬성 | 승인 → 그 팀의 팀원이 됨 |
| 한 명이라도 거부 | 다른 팀원을 기다리지 않고 **바로 거절** |
| 아직 투표하지 않은 팀원 있음 | 대기 |
| 투표 바꾸기 | 한 번 투표하면 **바꿀 수 없음** |

> 내가 지원한 뒤에 다른 지원자가 먼저 승인되어 팀원이 되면, **그 사람도 내 지원에 투표한다.**

### 5.2 승인 직전 재검사 (3장 어려운 해결, 3점)

모든 팀원이 찬성해 승인하려는 **그 순간에 규칙을 다시 검사**한다.

- 이유: 같은 팀에 대기 중인 지원이 여럿이면 앞의 지원이 먼저 승인되어 팀 상태가 바뀐다.
- 다시 검사하는 항목: **정원**, **주 역할 중복**, **필수 포함 역할 자리**.
- 어기게 되면 그 지원은 **거절**.
- 처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**.
- 그 전에는 대기 중인 지원을 미리 거절하지 않는다.

검증 예시(부록 3, 6~8단계): 학생5·학생6이 차례로 팀2에 지원 → 둘 다 대기 → 학생5 승인(팀2에 웹 프로그래머 들어옴) → 학생6은 승인 직전 검사에서 주 역할 중복 → **거절** ✓

### 5.3 지원이 막히는 경우 (2.4절·2.8절)

| 막히는 이유 | 화면 처리 |
| --- | --- |
| 이미 팀이 있음 | **지원 단추를 숨기거나 비활성화** (필수) |
| 결과를 기다리는 지원이 있음 | **지원 단추를 숨기거나 비활성화** (필수) |
| 모집이 마감됨 | **지원 단추를 숨기거나 비활성화** (필수) |
| 팀이 꽉 참(4명) | 단추를 눌러 "막힘" 안내 또는 단추 숨김 |
| 같은 주 역할의 팀원이 있음 | 단추를 눌러 "막힘" 안내 또는 단추 숨김 |
| 필수 포함 역할 자리 모자람 | 단추를 눌러 "막힘" 안내 또는 단추 숨김 |

- 채점 프로그램은 단추가 **없거나 비활성이면 "막힘"으로 본다**.
- 막힌 지원은 팀원의 투표 없이 끝나며 **DB에 기록하지 않아도 된다**.

### 5.4 "막힘"과 "거절"의 차이

| 구분 | 뜻 | 안내 시작 단어 |
| --- | --- | --- |
| 막힘 | 지원을 **아예 접수하지 않음** | `막힘` |
| 거절 | 접수되어 대기 중이던 지원이 팀원의 거부·승인 직전 검사·모집 마감으로 떨어짐 | `거절` |

## 6. 마감과 AI 배정 (2.5절)

| 단계 | 내용 |
| --- | --- |
| 1 | 관리자가 **모집 마감**을 누름 → 그 뒤로는 지원·투표 불가 |
| 2 | 마감 때 **대기 중인 지원은 거절**. **1명뿐인 팀의 학생은 팀에서 빠져** "팀이 없는 학생"이 됨 |
| 3 | 관리자가 **AI 배정**을 누르면 앱이 AI에게 (지금의 팀 구성 + 팀이 없는 학생과 역할 + 2.3절 규칙)을 보내 배정안을 받음. **팀이 없는 학생만** 넣고 **기존 팀원은 옮기지 않음** |
| 4 | 앱이 배정안을 **5가지로 검사** (아래 6.1절) |
| 5 | AI가 응답 없음 / 빈 응답 / 오류 / 검사 실패 → **2차 → 3차 모델**로 자동 재시도. 모델 하나당 **120초 전체 대기 시간**을 넘기면 끊고 다음 모델로 |
| 6 | 3차까지 실패하면 **앱이 스스로 배정** (3장 어려운 해결: 완전 탐색) |
| 7 | **검사를 통과한 배정안만** 관리자에게 보여 줌(학생 이름·역할·배정된 팀). 확정하면 DB에 저장 |
| 8 | 규칙을 모두 지키는 배정이 아예 없으면 배정안을 만들지 않고 `assign_status`에 "규칙을 지키는 배정이 없음" + 이유(예: 팀3에 웹 프로그래머를 맡을 학생이 없음). 이때는 **AI를 부르지 않아도 됨** |

### 6.1 배정안 검사 5가지 (2.5절 4항)

1. 팀이 없는 학생이 **빠짐없이** 배정됨
2. 한 학생은 **한 팀에만** 배정됨
3. 모든 팀이 **2~4명**
4. 팀 안에서 **주 역할 중복 없음**
5. **필수 포함 역할 충족** (기획자·웹 프로그래머, 서로 다른 사람)

### 6.2 명단 올리기 (2.6절)

관리자 화면에서 명단 CSV + 팀 수를 넣으면 앱 상태가 **초기화**된다.

- 지우는 것: 지원, 투표, 팀원, 마감 표시
- 만드는 것: 명단의 학생, 넣은 팀 수만큼의 **빈 팀**
- 남기는 것: **관리자 계정**
- 채점자가 시나리오마다 명단을 바꾸는 기능이므로 **없으면 채점 자체가 불가능**하다.

## 7. 화면 명세

### 7.1 Streamlit `key` 표 (2.7절 전체)

채점 프로그램은 화면 요소를 **Streamlit `key`로만** 찾는다. 아래 `key`를 **그대로** 지정해야 한다. 화면에 보이는 글자는 자유롭게 써도 된다.

| # | 화면 요소 | Streamlit 요소 | `key` |
| --- | --- | --- | --- |
| 1 | 학번 입력칸 | `st.text_input` | `login_student_no` |
| 2 | 비밀번호 입력칸 | `st.text_input` | `login_password` |
| 3 | 로그인 단추 | `st.button` 또는 `st.form_submit_button` | `login_submit` |
| 4 | 로그인한 사람 표시(이름이 보임) | `st.container` | `whoami` |
| 5 | 단추를 누른 결과 안내 | `st.container` | `result` |
| 6 | 팀 하나의 표시(팀원의 이름이 보임) | `st.container` | `team_1`, `team_2`, … |
| 7 | 팀에 지원하는 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 8 | 지원에 찬성하는 단추 | `st.button` | `vote_yes_{지원자 학번}` (예: `vote_yes_2026306`) |
| 9 | 지원에 거부하는 단추 | `st.button` | `vote_no_{지원자 학번}` |
| 10 | 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 11 | 팀 수 | `st.number_input` | `admin_team_count` |
| 12 | 명단으로 처음 상태 만들기 단추 | `st.button` | `admin_start` |
| 13 | 모집 마감 단추 | `st.button` | `admin_close` |
| 14 | 팀이 없는 학생 표시(이름이 보임) | `st.container` | `unassigned` |
| 15 | AI 배정 단추 | `st.button` | `admin_assign` |
| 16 | AI 배정 진행 안내 | `st.container` | `assign_status` |
| 17 | 배정안 확정 단추 | `st.button` | `admin_confirm` |
| 18 | 새로 고침 단추 — "다른 사람의 변경 보기"를 **쉬운 해결**로 만든 앱만 | `st.button` | `refresh` |

**18번에 대한 우리 앱의 방침**: 우리는 "다른 사람의 변경 보기"를 **어려운 해결**(`st.fragment` 자동 갱신)로 만들므로 `refresh` 단추는 **필수가 아니다**. 다만 채점 프로그램은 이 단추가 **있으면 먼저 누르므로**, 두어도 해롭지 않다. 둘 경우 학생 화면과 관리자 화면에 **모두** 두어야 한다.

### 7.2 `key` 관련 필수 주의

- `key`에는 **영문·숫자·밑줄만** 쓴다. 한글 `key`는 채점 프로그램이 찾지 못한다.
- `team_1`의 번호는 관리자가 명단을 올릴 때 만든 팀1, 팀2, …의 번호이며 시나리오의 팀 번호와 같다.
- `key`를 표와 다르게 지정하거나 지정하지 않아 채점 프로그램이 멈추면 **-5점**(6.3절 15번).
- `st.container`에 `key`를 주는 방법: `st.container(key="result")`.

### 7.3 `result` 안내 규칙

- 안내는 반드시 `승인` / `대기` / `거절` / `막힘` 중 하나로 **시작**한다.
- 이유를 함께 보여 준다. 예: `막힘: 같은 주 역할의 팀원이 있음`
- `result`는 **단추를 누른 사람의 화면**에 보인다.
  - 지원 단추 → 그 지원의 결과
  - 찬성/거부 단추 → 그 지원의 지금 상태(승인·대기·거절)
- 관리자 단추(명단 올리기·마감·AI 배정·확정)도 해냈으면 `승인`, 못 했으면 `막힘`으로 시작한다. 예: `승인: 모집을 마감함`
- 한 단계에 동작이 여럿이면 채점 프로그램은 **동작마다** `result`를 확인한다.

### 7.4 학생 화면 (2.8절)

- 팀 목록에서 로그인한 학생의 팀을 구별되게 표시(예: 팀 이름 옆에 "내 팀"). 팀이 없으면 "아직 팀이 없음". (이 표시는 채점하지 않음)
- **팀 목록은 팀마다 팀원의 이름과 역할을 함께 보여 준다.** 역할은 주 역할과 보조 역할을 구분해 적는다. 예: `가나다 — 주: 기획자 / 보조: 보고서 작성자`
- **학생 이름은 명단 CSV의 `name` 값을 그대로** 표시한다. 줄이거나 바꾸거나 학번으로 대신하지 않는다 (채점 프로그램이 `team_N`과 `unassigned`에서 이름으로 확인한다).
- 이미 팀에 속함 / 결과를 기다리는 지원 있음 / 모집 마감 → **지원 단추 숨김 또는 비활성화**
- 이미 투표한 지원 → 그 학생의 찬성·거부 단추를 숨기거나 비활성화하고 "내 투표: 찬성"처럼 보여 준다.

### 7.5 관리자 화면

관리자 화면은 **세 부분으로 나눈다** (시연 영상의 시범 앱과 같은 구성).

| 부분 | 들어가는 것 |
| --- | --- |
| **1. 명단 올리기** | `admin_roster_file`(CSV 업로더), `admin_team_count`(팀 수), `admin_start`(처음 상태 만들기) |
| **2. 마감과 배정** | `admin_close`(모집 마감), `admin_assign`(AI 배정), `assign_status`(진행 안내), 배정안 표, `admin_confirm`(배정안 확정) |
| **3. 현황** | 팀 목록(`team_1`, `team_2`, …), `unassigned`(팀이 없는 학생), 대기 중인 지원 목록 |

세부 규칙:

- `unassigned`에는 **팀이 없는 학생의 이름**을 보여 준다.
- 마감 때 대기 지원이 거절되고 1명뿐인 팀의 학생이 빠진 결과를 채점 프로그램이 `unassigned`로 확인한다.
- "규칙을 지키는 배정이 없음" 안내는 `assign_status` 안에 보여 준다.
- **AI 배정 중**에는 `assign_status`에 **몇 차 모델을 기다리는 중인지** 보여 준다. 예: `2차 모델의 응답을 기다리는 중 (45초 경과)` (3장 어려운 해결 7번, 1점)
- **배정안이 규칙 검사 5가지를 통과하면** 관리자에게 **표**로 보여 준다:

  | 학생 이름 | 주 역할 | 보조 역할 | 배정된 팀 |
  | --- | --- | --- | --- |
  | (CSV의 `name` 그대로) | 기획자 | 보고서 작성자 | 팀3 |

- 표 아래에 `admin_confirm`(배정안 확정) 단추를 두고, 누르면 DB에 저장한다.
- **확정한 뒤에는 `unassigned` 목록이 비어야 한다.** 팀이 없는 학생이 모두 팀에 들어갔다는 뜻이며, 채점 프로그램이 이것으로 배정 결과를 확인한다.
- 검사를 통과하지 못한 배정안은 표에 **보여 주지 않는다**.

### 7.6 자동 갱신

- 어려운 해결: `st.fragment`로 **5초 이하 간격**으로 바뀐 부분만 다시 그린다.
- 채점 프로그램은 단추가 나타나기를 **7초까지** 기다린다.
- **화면 맨 위에 "화면은 5초마다 저절로 바뀜" 안내를 보여 준다.** 학생 화면과 관리자 화면 모두에 둔다. 사용자가 새로 고침을 누르지 않아도 다른 사람의 지원·투표가 나타난다는 것을 알려 주는 표시다.
- 자동 갱신 범위는 **팀 목록과 지원 현황으로 좁힌다**. 입력칸·파일 업로더가 든 영역까지 다시 그리면 입력 중인 값이 날아간다.

### 7.7 시각 표시

배포 서버(Streamlit)의 시각은 **UTC**다. 화면에 시각을 보여 줄 때는 **KST(UTC+9)로 변환**해 보여 준다.

## 8. 3장 기능별 선택 — **전부 어려운 해결**

| # | 기능 | 쉬운 해결 (안 씀) | **우리가 만들 어려운 해결** | 점수(쉬움, 어려움) |
| --- | --- | --- | --- | --- |
| 1 | 다른 사람의 변경 보기 | 새로 고침 단추 | **`st.fragment`로 바뀐 부분만 5초 이하 간격 자동 갱신** | 0.5점, **1점** |
| 2 | 필수 포함 역할을 지킬 수 없는 팀 | 배정 단계에서 "규칙을 지키는 배정 없음" 안내 | **지원 단계에서, 필수 포함 역할을 채울 자리가 모자라게 되는 지원을 막음** (4.2절 공식) | 1.5점, **7점** |
| 3 | 같은 팀에 대기 중인 지원이 여럿 | 지원할 때만 검사 | **승인 직전에 규칙 재검사. 처리 순서는 투표가 끝난 순서** | 0점, **3점** |
| 4 | 마지막 자리에 두 명이 동시에 들어감 | 앱이 인원을 센 뒤 넣음 | **DB 유일성 제약으로 먼저 도착한 학생만 기록** (`tf_members`) | 0점, **0.5점** |
| 5 | AI 응답이 늦을 때 | 요청 함수에 시간 제한 값만 줌 | **모델마다 120초 전체 대기 시간을 재서 끊고 다음 모델로** | 0.5점, **1점** |
| 6 | 3차 모델까지 실패 | 자리 남은 팀에 무작위로 넣음 | **검사 5가지를 모두 통과하는 배정을 모든 경우를 따져 끝까지 찾음** | 쉬운 해결은 확정 뒤 규칙 점수 최대 **6.5점** 손실 가능 |
| 7 | AI 대기 중 화면 | "AI가 생각하는 중" | **몇 차 모델의 응답을 기다리는 중인지 표시** | 0.5점, **1점** |
| 8 | DB(Supabase)가 일시정지되지 않게 | 마감 날 앱을 써서 요청 만듦 | **외부 예약 서비스로 매일 DB에 질의를 보냄** | 0점, **0.5점** |

> 2번(7점)과 6번(최대 6.5점)이 가장 배점이 크다. 구현 계획에서 가장 많은 시간을 배분한다.

## 9. 데이터 모델 (5장)

### 9.1 테이블

모든 테이블 이름은 **`tf_`로 시작**한다(6.3절 13번, -1점). 6장 실습 테이블과 같은 Supabase 프로젝트를 쓰기 때문이다.

| 테이블 | 열 | 뜻 |
| --- | --- | --- |
| `tf_students` | `id`, `student_no`(학번, 유일), `name`, `main_role`, `password_hash`, `is_admin` | 학생과 관리자 |
| `tf_student_sub_roles` | `student_id`, `role` | 보조 역할. 학생 1명에 0~2행 |
| `tf_teams` | `id`, `name`(유일) | 팀 |
| `tf_members` | `team_id`, `slot_no`(1~4), `student_id`(유일) | 팀원. `(team_id, slot_no)`를 기본 키로 |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`(대기/승인/거절), `reason`, `created_at` | 지원 |
| `tf_votes` | `application_id`, `voter_id`, `vote`(찬성/거부) | 투표. `(application_id, voter_id)`를 기본 키로 |
| `tf_settings` | `key`, `value` | 마감 여부 등 |

### 9.2 추가할 테이블·열

| 추가 | 이유 |
| --- | --- |
| `tf_ai_logs` | AI 호출 기록. 열: `called_at`(시각), `attempt_no`(몇 차 모델, 앱 자체 배정은 4), `model`, `outcome`(성공/시간초과/빈 응답/오류/검사 실패), `fail_reason`, `elapsed_ms`, `response_excerpt`. **호출이 실패할 때마다 한 행을 남긴다.** README 7.1절 5항 사례의 근거로 쓴다 |
| `tf_applications.resolved_at` | 승인 직전 재검사의 **처리 순서(투표가 끝난 순서)** 판단에 쓴다 |

### 9.3 제약 (점수와 직결)

| 제약 | 효과 |
| --- | --- |
| `tf_members (team_id, slot_no)` 기본 키 | 같은 자리에 두 명이 못 들어감 |
| `tf_members.student_id` 유일 | 한 학생은 한 팀에만 소속 |
| `slot_no` 에 `check (slot_no between 1 and 4)` | 다섯 번째 자리 차단 |
| `main_role`, `role` 에 역할 6개만 허용하는 `check` | 6개 역할 밖의 값 차단 |
| `tf_votes (application_id, voter_id)` 기본 키 | 투표 바꾸기 차단 |

### 9.4 `schema.sql` (필수 제출물)

저장소 루트에 `schema.sql`을 **반드시** 남긴다. 채점자는 학생의 Supabase를 볼 수 없으므로 이 파일로 확인한다.

| 없으면 잃는 것 |
| --- |
| DB 유일성 제약 점수 0.5점 |
| 테이블 이름 확인 불가 → 6.3절 13번 적용(-1) |
| 비밀번호 해시 열 확인 불가 → 6.3절 10번 적용(-2) |

- Supabase SQL 편집기에서 직접 만든 SQL도 `schema.sql`에 넣는다.
- 앱이 실제로 쓰는 테이블·열·제약과 **같은지 확인**한다.

### 9.5 DB 연결 성능

질의마다 연결을 새로 만들면 화면이 몇 초씩 느려진다(연결 0.5초 × 질의 10번 = 5초). **연결은 한 번만 만들고 재사용**한다(`st.cache_resource`).

## 10. AI 모델 (4.3절)

| 항목 | 방침 |
| --- | --- |
| 공급자 | OpenRouter 텍스트 생성 모델 |
| 개수 | **3개**를 1차·2차·3차로 직접 정함 |
| 권장 | 무료 모델(이름이 `:free`로 끝남). 유료도 감점 없으나 요금은 본인 부담 |
| 금지 | **`openrouter/free` 라우터 사용 금지** (6.3절 14번, -2점). 다음 모델로 넘어가는 처리를 직접 만드는 것이 과제의 일부 |
| 실패 판정 | 응답 없음, **빈 응답**, 오류(HTTP 429 등), 배정안이 검사 5가지를 통과하지 못함 |
| 시간 제한 | 모델 하나당 **120초 전체 대기 시간** |
| 빈 응답 줄이기 | `reasoning effort`를 `low`로, `max_tokens`를 넉넉히 |

> 1차·2차·3차 모델의 정확한 이름은 구현 6단계에서 OpenRouter의 모델 목록을 직접 확인한 뒤 확정한다. 무료 모델 목록은 수시로 바뀌므로 미리 적어 두지 않는다.

### 10.1 무료 모델 호출 한도 — 채점 대비

| 항목 | 값 |
| --- | --- |
| 한도 | 계정당 **하루 50회, 분당 20회**. 실패한 호출도 포함 |
| 연습 1회 비용 | 연습 시나리오 3개를 한 번 돌리면 AI 호출 3~9번 |
| **채점 기간 대비** | 11/3~11/4에는 채점자가 내 키로 AI를 부른다. **그 이틀 동안 하루 한도 중 30번 이상을 남겨 둬야 한다** |
| 시간대 주의 | 무료 모델은 **밤에 더 자주 실패**한다. 연습은 낮에 |

### 10.2 채점되는 것

채점은 AI 배정의 **내용**이 아니라 (1) 확정한 팀 구성이 규칙을 지키는지, (2) **실패를 처리했는지**를 본다. 실패 처리는 모델마다 120초 제한 / 2차·3차로 넘어감 / 3차까지 실패하면 앱이 스스로 배정함을 **화면 기록이나 코드로** 확인한다. → `tf_ai_logs`와 `assign_status` 화면을 남겨 둔다.
