# 팀 편성 웹 앱 — 중간 과제 대체 보고서

학생들이 스스로 팀에 지원하고 투표해 팀을 만들고, 마감 뒤 남은 학생은 AI가 배정안을 내고
**앱이 그 배정안을 규칙으로 검사**하는 Streamlit 웹 앱.

## 3. 고른 해결 방법 (3장 표) — 8개 모두 **어려운 해결**

| 기능 | 고른 해결 | 어떻게 만들었는지 |
| --- | --- | --- |
| 다른 사람의 변경 보기 | **어려운 해결** | `st.fragment(run_every=5)` 로 팀 목록·지원 현황만 5초마다 다시 그림. 새로 고침 단추(`refresh`)는 두지 않음 |
| 필수 포함 역할을 지킬 수 없는 팀 | **어려운 해결** | 지원 단계에서 막음. `남는 자리 < 못 채운 필수 역할 수` 면 거절 (`rules.required_slot_short`) |
| 같은 팀에 대기 중인 지원이 여럿 | **어려운 해결** | 모든 팀원이 찬성한 그 순간 규칙을 다시 검사 (`rules.check_approve`). 처리 순서는 투표가 끝난 순서(`tf_applications.resolved_at`) |
| 마지막 자리에 두 명이 동시에 들어감 | **어려운 해결** | `tf_members` 의 `(team_id, slot_no)` 기본 키와 `student_id` 유일 제약으로 먼저 도착한 쪽만 기록 ([schema.sql](schema.sql)) |
| AI 응답이 늦을 때 | **어려운 해결** | 응답을 조금씩 받으며 경과 시간을 재서, 부른 때부터 **전체 120초**를 넘기면 끊고 다음 모델로 (`ai.call_model`) |
| 3차 모델까지 실패 | **어려운 해결** | 검사 5가지를 모두 통과하는 배정을 가지치기 완전 탐색으로 끝까지 찾음 (`assign.solve`) |
| AI 대기 중 화면 | **어려운 해결** | `assign_status` 에 "N차 모델의 응답을 기다리는 중" 과 "N차 모델 실패(이유) → 다음 모델로 넘어감" 을 지우지 않고 쌓아서 보여 줌 |
| DB(Supabase)가 일시정지되지 않게 | **어려운 해결** | GitHub Actions 로 매일 한국 시각 09:00 에 DB 질의 ([.github/workflows/db-keepalive.yml](.github/workflows/db-keepalive.yml)) |

## 6. 클로드가 잘못된 추론이나 답변을 한 사례

전체 기록은 [docs/작업기록.md](docs/작업기록.md) 에 11건 있다. 영향이 큰 두 건.

**사례 1 — 기능 하나를 빠뜨리고 "4단계 끝났다" 고 보고함** (작업기록 9번)

클로드가 4단계(지원·투표)를 끝냈다고 보고하고 5단계로 넘어갔는데, 3장 표의 1번 기능
**"다른 사람의 변경 보기"(어려운 해결 1점)를 만들지 않았다.** 새로 고침 단추도 없고
자동 갱신도 없어서, 다른 학생의 지원이 내 화면에 아예 나타나지 않는 상태였다.
이대로라면 채점 프로그램이 지원·투표를 보지 못해 그 자리에서 멈춘다.

- **알아챈 방법**: 9단계 자동 테스트를 만들면서 "학생마다 창을 따로 쓰면 다른 학생의
  지원이 어떻게 보이지?" 를 따져 보다가, 계획서 4-4단계의 확인 항목이 통째로 빠진 것을 찾았다.
- **고친 커밋**: `3cca978` — `st.fragment(run_every=5)` 로 팀 목록과 지원 현황만 5초마다
  다시 그리게 했다. 화면 맨 위에 "화면은 5초마다 저절로 바뀜" 안내도 넣었다.
  입력칸과 파일 업로더는 조각에 넣지 않았다(다시 그리면 입력 중인 값이 날아간다).

**사례 2 — DB 연결을 전원이 하나로 공유하게 만듦** (작업기록 10번)

공고 4.2절의 "연결은 한 번만 만들고 다시 써라" 를 클로드가 **"연결을 딱 하나만 만들어
모든 사용자가 공유"** 로 구현했다. 화면이 5초마다 갱신되므로 학생 여러 명이 접속하면
질의가 한꺼번에 몰리는데, 그 결과

1. 한 사람의 묶음 처리(트랜잭션) 도중에 다른 사람의 질의가 끼어들어
   `psycopg.errors.InFailedSqlTransaction` 오류가 번졌고,
2. 질의가 줄을 서느라 화면 갱신이 몇 초씩 늦어져 투표 단추가 제때 나타나지 않았다.

채점 때는 가상 학생 8~16명의 브라우저가 동시에 열리므로 그대로 두면 채점 중에 화면이 깨진다.

- **알아챈 방법**: 자동 테스트에서 투표 단추를 못 찾아 계속 "막힘" 이 나왔다. 앱을 혼자
  열어 보면 잘 되는데 테스트에서만 안 되는 것이 이상해서 **서버 기록**을 읽었더니
  `current transaction is aborted` 가 수십 번 쌓여 있었다.
- **중간에 또 틀림**: 자물쇠(lock)로 한 명씩 쓰게 고쳤더니 오류는 사라졌지만 질의 10번이
  0.797초에서 **2.289초**로 늘어 화면이 더 늦어졌다. 이것도 틀린 처방이었다.
- **고친 커밋**: `3cca978` — 연결 풀(`psycopg_pool`, 2~10개)로 바꿨다. 질의마다 새로
  연결하는 것이 아니므로 공고가 경고한 느려짐은 생기지 않는다. 풀 연결을 autocommit 으로
  두어 질의 하나마다 묶음을 여닫는 왕복도 없앴다. 고친 뒤 질의 10번이 **0.756초**로
  돌아왔고, 자동 테스트의 투표 단추 문제도 모두 사라졌다.

> 공고 문구와 다른 점: 연결을 "하나" 가 아니라 **2~10개 풀**로 쓴다. 공고가 막으려는
> 것(질의마다 새 연결)은 지켰지만, 문구 그대로는 아니다.

**사례 3 — 배포한 앱이 "비공개" 라고 잘못 단정함** (작업기록 12번)

배포 주소로 자동 테스트를 돌렸더니 접속 단계에서 멈췄다. 클로드가 `curl -I -L` 로
확인했는데 Streamlit 로그인으로 **무한 리다이렉트**되는 것을 보고
"공개 설정이 안 됐다, 이대로면 시나리오 점수 0점" 이라고 단정해 보고했다.

**그런데 앱은 처음부터 공개 상태였다.** Streamlit Community Cloud 는 공개 앱이라도
처음 접속할 때 쿠키를 받는 리다이렉트를 한다. `curl -I`(머리글만 받기) 에 쿠키 저장
옵션도 없이 확인했으니, 쿠키를 못 받아 같은 자리를 맴돈 것이다.

- **알아챈 방법**: 사용자가 "휴대폰 데이터로 열면 학번/비밀번호 화면이 바로 뜬다" 고
  알려 주어 다시 확인했다. 쿠키를 저장하며(`curl -L -c -b`) 접속하니 **HTTP 200** 이었고,
  브라우저 화면을 찍어 보니 로그인 화면이 멀쩡히 보였다.
- **배운 점**: 쿠키를 주고받는 사이트는 `curl -I` 나 쿠키 없는 요청으로 판단하면 안 된다.
  "리다이렉트가 반복된다" 는 관찰은 맞았지만, 거기서 끌어낸 결론이 틀렸다.
  사용자에게 "0점이 된다" 고까지 말했으므로, 확인 방법을 먼저 의심했어야 했다.
- **고친 커밋**: `40c631c` — 잘못 적은 내용을 `docs/테스트결과.md` 에서 지우고
  사실대로 다시 적었다. 자동 테스트에는 잠든 앱을 깨우는 처리와 넉넉한 대기 시간을 넣었다.

## 7. 내 앱에서 발견한 문제점·개선 필요 사항

**문제 1 — 1차 모델이 자주 빈 응답을 내서 배정이 1~2분 늦어진다**

연습 시나리오 3개를 돌렸을 때, 당시 1차였던 `nvidia/nemotron-3.5-lightning:free` 가
**5번 불러 한 번도 성공하지 못했다**(빈 응답 3번, 배정안 검사 실패 2번).
그래서 매번 2차 모델로 넘어가야 했고, 2차는 120초를 넘겨 끊기는 일이 잦아
배정 한 번에 **1~2분이 더 걸렸다**.

- **발견한 단계**: 부록 1·2·3의 마지막 배정 단계(쉬움 6단계, 중간 11단계, 어려움 15단계)
  — [docs/테스트결과.md](docs/테스트결과.md)
- **근거 화면**: [img/ai-call-log-with-title.png](img/ai-call-log-with-title.png)
  — 관리자 "현황" 의 AI 호출 기록 표. 1차(`lightning`)가 빈 응답을 내고 2차로 넘어가는
  일이 16:10, 16:19 등에 되풀이된 것이 그대로 보인다.
  원본 기록은 [docs/AI호출기록.csv](docs/AI호출기록.csv)
- **근거 수치**: `tf_ai_logs` 모델별 집계 — `lightning` 호출 5번 / 성공 0번
- **개선**: 성공 평균이 62.5초인 `dots-studio/dots-3-note-preview:free` 를 1차로 올리고
  lightning 을 뺐다(커밋 `8cdee0e`).
- **개선 뒤 확인 화면**: [img/assign-status-success.png](img/assign-status-success.png)
  — 바꾼 뒤 같은 명단(쉬움 8명, 팀 3개)으로 다시 배정해 보니
  **1차 모델이 한 번에 검사 5가지를 통과**했다. 진행 안내에 적힌 그대로다.

  ```
  팀이 없는 학생 8명. 규칙을 지키는 배정이 있는지 확인하는 중
  확인에 0.0초 걸림
  규칙을 지키는 배정이 있음. AI에게 배정안을 받는다
  1차 모델의 응답을 기다리는 중
  1차 모델의 배정안이 검사 5가지를 모두 통과함
  ```

  다만 **남은 모델들도 성공률이 25~50%** 라 배정이 느려지는 문제 자체는 남아 있다.
  무료 모델의 한계로 보인다. 한 번 성공했다고 해결된 것은 아니다.

**문제 2 — 오류가 나면 화면에 오류 추적(Traceback)이 그대로 보였다**

3단계에서 단추를 눌렀을 때 `AttributeError ... Traceback ... File "streamlit_app.py",
line 224` 가 화면에 그대로 나왔다. 채점 중에 이러면 채점 프로그램이 `result` 안내를
읽지 못해 그 자리에서 멈춘다.

- **발견한 단계**: 3단계 명단 올리기를 브라우저에서 시험하던 중
- **개선**: 모든 단추가 지나는 공통 처리(`run_action`)를 만들어, 어떤 오류가 나도
  화면에는 `막힘: ...` 만 보여 주고 자세한 내용은 서버 기록에만 남기게 했다
  (커밋 `e0c1d8a`, `6352243`).

**문제 3 — 배정 대상이 8명을 넘으면 완전 탐색이 느려질 수 있다**

`assign.solve` 는 가지치기를 넣은 완전 탐색이다. 어려움 시나리오(배정 대상 8명)에서는
**0.0초**에 끝났지만, 공고 6.2절 9항이 보장하는 8명을 넘는 명단이 들어오면 느려질 수 있다.

- **발견한 단계**: 6단계 확인 중 탐색 시간을 재면서
- **지금 상태**: `solve` 에는 **시간 제한이 없다.** 배정 전체의 시간 제한(9분)은 AI를
  부르는 부분에만 걸려 있고, 탐색에는 걸리지 않는다. 지금은 "팀이 없는 학생이 8명을
  넘지 않는다"는 공고 6.2절 9항에 기대고 있을 뿐이다.
- **개선 필요**: 탐색에도 시간 제한을 두고, 시간이 다 되면 그때까지 찾은 결과가 없을 때
  "규칙을 지키는 배정이 없음" 대신 "시간 안에 찾지 못함"으로 구분해 안내해야 한다.

## 9. 직접 돌려 보는 방법

```bash
pip install -r requirements.txt
streamlit run streamlit_app.py
```

`.env` 에 `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD` 가 필요하다
(저장소에는 올라가 있지 않다). 배포한 앱은 같은 이름을 Streamlit Secrets 에서 읽는다.

연습 시나리오 자동 테스트:

```bash
pip install -r tests/requirements.txt
python -m playwright install chromium
python tests/run_scenarios.py --all --out docs/테스트결과.md
python tests/check_rules.py
```

`tests/` 폴더의 파일은 **앱이 절대 읽지 않는다**(공고 6.3절 19번).
기대 결과를 앱에 알려 주지 않으며, 앱은 규칙만 보고 판단한다.
